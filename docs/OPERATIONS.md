# Recipe MCP operations

## Supported deployment

One application process, one trusted tenant, and a persistent local SQLite database. Use stdio for desktop integrations or HTTPS with a bearer-capable client for private HTTP. Shared-token authentication does not implement the MCP OAuth authorization specification. A public multi-user deployment requires identity, authorization and tenant ownership before exposure.

## Local container

Set `RECIPE_AUTH_TOKEN` in your private `.env` to a generated token (at least 32 visible ASCII characters). Then run:

```bash
docker compose up --build -d
curl http://127.0.0.1:8000/readyz
docker compose logs --tail=50
```

The named volume stores `/data/recipes.sqlite3`. The image runs as UID 10001. A fresh Docker named volume inherits the image directory's ownership; for existing/bind-mounted volumes, provision write access for UID 10001. Do not remove the volume to update the application. `docker compose down` retains it; `down -v` removes it and the data.

## Render deployment

The included `render.yaml` describes a Docker service with one instance and a persistent disk. Push the extracted project to a repository you control and create a Render Blueprint from that repository. Review its service/disk costs before deploying. Supply:

- `RECIPE_ALLOWED_HOSTS`: a JSON array such as `["your-service.onrender.com","127.0.0.1","127.0.0.1:*"]`.
- `RECIPE_ALLOWED_ORIGINS`: a JSON array with the trusted browser origins, such as `["https://your-service.onrender.com"]`. Non-browser MCP clients usually omit Origin.
- `RECIPE_API_KEY`: `1` for an educational demo, or your provider key for the intended use.

The token is generated by Render; retrieve it only in your private service settings and pass it to your client as a bearer token. Use the public `https://.../mcp` URL. Render supplies `PORT`; the CLI and health check honor it. The initial mode is demo. For live mode, use a separate database path (for example `/data/live.sqlite3`) and set `RECIPE_MODE=live` to prevent fixture/live ID mixing.

Verify disk ownership and `/readyz` after startup. Persistent disk mounting may require configuring owner UID 10001 in the target environment. This blueprint is a deployment input, not proof of a completed cloud rollout.

Render disks are attached to one instance and prevent horizontal scaling; disk-backed redeployments may interrupt service. Files outside the mount are ephemeral. See [persistent disks](https://render.com/docs/disks) and [Blueprint reference](https://render.com/docs/blueprint-spec).

## Runtime behavior

- `/healthz` reports the process version and selected provider mode.
- `/readyz` verifies the database can be read. It does not probe TheMealDB or prove that future writes have disk space.
- HTTP protocol traffic needs the token if configured. Remote binding without a token fails startup.
- Host/Origin rules and a 64 KiB payload limit are enforced by the MCP HTTP adapter.
- The process-wide 120-request/minute admission quota excludes health checks, ignores untrusted proxy headers, and resets on restart. Put any tenant-specific or distributed quotas at an authenticated gateway.
- Logs go to stderr. HTTP library INFO logging is disabled to avoid logging API keys embedded in upstream paths. Access logs are disabled by default. Log unexpected exception types rather than raw provider responses.
- SDK discovery, tool annotations and prompt text guide clients; they do not enforce a host's user confirmation experience.

## Backup and recovery

Do not copy only the main SQLite file while the app is running in WAL mode. Use SQLite's backup API:

```bash
uv run python scripts/backup.py data/recipes.sqlite3 backups/recipes-2026-09-19.sqlite3
```

Choose a new output filename for each backup. The script opens the source read-only, uses a consistent SQLite backup and runs `PRAGMA integrity_check`. Copy completed backups to your chosen durable backup destination and test recovery before relying on them. Retention, off-host transfer and scheduling are operational responsibilities.

To restore, stop the service first, retain the current database and any `-wal`/`-shm` files together as a recovery copy, and configure `RECIPE_DATABASE_PATH` to the verified backup copy. Ensure no old sidecar files exist at the new destination. Start the service, check `/readyz`, read statistics and sample saved plans. Never restore over an active database. The schema version is checked on startup; unsupported future schema versions fail rather than silently rewriting data.

## Dependency updates

`uv.lock` captures resolved versions. `requirements.lock` is its hash-checked, production-only export used by the Dockerfile. Update them together:

```bash
uv lock --upgrade
uv sync --locked
uv export --locked --no-dev --no-emit-project --format requirements-txt --output-file requirements.lock
uv run pytest
uv run mypy
uv run ruff check .
```

Review major-version migration guides before widening dependency constraints. Build and exercise the image in your deployment environment after dependency changes.

## Scaling and recovery limits

SQLite commits writes serially. Database calls run in worker threads and use a busy timeout; this is not a substitute for measuring contention. Idempotency keys are retained with their plans and currently have no expiration or cleanup job. Recipe snapshots persist until refreshed by a new fetch; TTL applies only to provider memory. There is no automatic database retention policy.

For multiple users or replicas, introduce OAuth with audience/scope checks, per-user authorization, PostgreSQL, migration tooling and measured service objectives. Add a distributed cache only when measured quotas or duplicated traffic justify it. No load capacity, uptime, RPO or RTO is claimed by this portfolio build.
